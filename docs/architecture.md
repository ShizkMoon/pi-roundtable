# Architecture

## 1. Deployment model

A meeting is controlled by one Runtime Host. In the first implementation cycle that host runs beside the Windows application and embeds Pi through its supported SDK surface. Pi is the only supported model runtime. Linux hosts the optional synchronization plane: normalized event storage, lease fencing, replay cursors, signed device-token authentication, audience-filtered private delivery, and optional PostgreSQL persistence. Client remote integration, E2EE, TLS/rate-limit deployment, multi-replica notifications, and push remain pending. Android is a presentation and control client and never launches Pi locally.

This split avoids two conflicting sources of truth. If a runtime moves to another machine, the sync server increments `runtimeGeneration`; events from the old generation are rejected even if the old process reconnects late.

## 2. Components

### Protocol

`protocol/schema` is the wire contract. Every persisted event contains a protocol version, meeting ID, monotonic sequence, runtime generation, event kind, occurrence time, an explicit public/private visibility lane, and a normalized payload. Private events require a non-empty unique audience; public events must not carry one. The TypeScript boundary exposes runtime validators for untrusted command/event JSON, and the Windows C ABI carries the audience into the C++ reducer instead of discarding it; the core rejects a private audience that omits a routed sender/recipient. Platform clients must tolerate unknown payload keys but must reject unsupported protocol major versions. Public events are meeting context; private events may be observed only by their declared audience.

### C++ meeting core

`core` applies ordered events and enforces deterministic meeting invariants. It does not parse Pi events, open sockets, access storage, or render UI. A narrow C ABI makes the reducer consumable from native shells without exporting C++ ABI details.

### Runtime Host

`packages/runtime-host` defines a domain-neutral runtime contract and owns all Pi SDK integration. The implemented `PiRuntimeAdapter` embeds the pinned Pi SDK directly. It creates one supervised session for one active role, injects provider credentials in memory, applies a cache-stable frozen role prefix, derives an automatic compaction threshold from the resolved model's actual context window, and forwards bounded provider cache retention/session affinity without exposing those controls in the public protocol. Default Skill discovery stays disabled: only participant-approved Skill paths load as native resources, and executable plugins enter through approved MCP grants. Raw Pi extensions are not supported in-process because they inherit host OS permissions. The MCP client boundary supports stdio, Streamable HTTP, and legacy SSE with bounded discovery/output, approved launchers, same-origin secure remote transport, and in-memory credential resolution. Raw Pi session records remain private.

The implemented local host owns one meeting-wide sequence and generation, creates one Pi session per active role, resolves provider/model/prompt/Skill/MCP inputs from validated workspace and participant manifests, processes normalized meeting commands, and performs cancel-then-handoff interruption over bounded stdio JSONL. An internal `RoleSessionSupervisor` binds each primary adapter and its planner, observer, and SubAgent children to an immutable role/generation/session token, registers stalled startups before awaiting them, filters retained callbacks, and closes the role credential lease when that resource scope retires. Host-owned queued public turns, interruption handoffs, observer decisions, and SubAgent continuations also carry that exact identity and are discarded when a same-ID role is recreated. The lease drops references and prevents later resolution; explicit zeroization of credential storage remains pending. A public host broadcast may target one or more roles for the next response while remaining visible to all participants; before dispatch, a separate in-memory Pi planning session with no tools, Skill, MCP, SubAgent, or role context extracts only exact source excerpts into hidden shared/per-role/subset routing and proposes the initial speaker order. Invalid or unavailable planning falls back to the explicit target order; the public event always retains the original message and does not expose the internal plan. A deterministic scheduler then owns agenda/free-discussion/convergence state, floor priority/fairness, per-segment budgets, and automatic convergence/pause. In free discussion, non-speaking roles may receive separate bounded Pi observation probes; probes have no tools or delegation, must cite an exact excerpt, and can only request the floor through the deterministic scheduler. Observer work uses a FIFO, abortable three-call concurrency gate; a distinct final probe is allowed when completion adds no text, while duplicate observations do not consume budget. Model completion time never chooses public order, and only a budgeted critical factual/safety/requirement/process correction may cancel an active speech. Responses remain serial on the public floor. A private host command runs in the selected role's isolated context and emits audience-scoped events without claiming the public floor. MCP tool callbacks honor `always`, `on_first_use`, and `never` approval modes; approval requests are private host events and omit tool arguments/results. An isolated Pi SubAgent cannot recurse, runs without MCP tools, is capped at two concurrent children per parent role, reports bounded progress, and returns its bounded text only to that parent. Automatic memory extraction and recall injection, prompt revision history, exact Pi private-session restoration, and OTel export remain planned. Runtime-specific mechanics stay below the neutral adapter even as those capabilities are added.

### Sync server

`packages/sync-server` provides an in-memory development store and an optional PostgreSQL store behind the same normalized-event contract. HTTP uploads events; SSE supplies foreground real-time updates and reconnect cursors. Every `/v1` route requires a signed bearer device token scoped to meeting IDs, audience identities, runtime IDs, and expiry. Private uploads require a non-empty unique audience, and replay/SSE applies that audience against the authenticated user/device/delegated identities. The PostgreSQL path applies an idempotent migration and performs lease acquisition, generation fencing, sequence allocation, and event writes transactionally. Without `DATABASE_URL`, the process reports `persistence: memory` and is not a production durability claim. Client-side encryption and key-envelope management routes, TLS termination, rate limits, retention jobs, and multi-replica LISTEN/NOTIFY remain pending.

### Native clients

Windows uses .NET 10 LTS with WinUI 3 and owns the implemented first local runtime integration. Its session-first shell persists non-secret workspace profiles, session groups, and frozen session definitions under Local AppData; stores provider and optional sync secrets in Windows Credential Manager; supervises the stdio Host; sends normalized commands; applies every event, including its private audience, to the C++ core; and projects accepted state into the UI. Accepted normalized events, checkpoints, and append-only role-memory revisions share a migrated SQLite store; event and memory content are protected by current-user DPAPI, and memory writes use revision compare-and-swap plus soft supersession. The memory management UI and runtime recall injection are not yet connected. A separate bounded `DocumentPipeline` safely recognizes inert Markdown/TeX, DrawIO XML, and macro-free DOCX/PPTX/XLSX packages; PDF remains signature-checked metadata-only. This pipeline is implemented and tested but is not yet attached to the message composer. On resume, the client validates that the checkpoint matches the event tail, replays the prior event stream through a fresh C++ reducer, reconstructs the latest discussion mode/agenda/counters/pending floor requests, passes that snapshot to the next Runtime Host, invalidates stale approvals/runs, and increments `runtimeGeneration` without pretending to restore Pi's private token/session state. Pause is a recoverable clean shutdown; close is terminal. A normal local meeting does not require a remote sync server. Android uses Kotlin/Compose Material 3 with layouts that adapt at 600 dp and 840 dp. Both consume normalized protocol models and never import Pi internals.

## 3. Interruption model

Interruption is not simulated by visually reordering chat messages. The authoritative event order is:

1. `speech.started` for the current speaker;
2. `interruption.requested` from another role;
3. `speech.cancelled` for the current generation;
4. `speech.started` for the interrupting role.

The core rejects a second interruption while one is pending, a cancellation targeting a non-speaker, and a new speaker that bypasses the pending handoff. The Pi adapter maps the normalized orchestration policy to supported prompt, steering, follow-up, and cancellation operations.

## 4. Role lifecycle

The meeting core distinguishes a long-term role from a meeting-scoped temporary role. Registration adds an active participant. A temporary role may be promoted once to long-term. Archiving removes the role from the active roster while retaining its meeting record; leaving removes that record. All transitions remain ordered meeting events and carry the active `runtimeGeneration`.

This implemented lifecycle is the deterministic meeting foundation. The Windows path now persists long-term role prompts, model routes, default auto-join behavior, and explicit Skill/MCP attachments, then freezes them into participant manifests. Exact per-tool allowlists are editable and deny by default: an empty allowlist exposes no tool. Approved MCP execution and expiring interactive host decisions are implemented through the Runtime Host and Windows approval panel. Durable encrypted memory contents and immutable memory revision history are implemented as a local storage foundation; automatic extraction, bounded recall injection, user-facing review, prompt revision history, live grant mutation events, and end-of-meeting retention workflows remain planned.

## 5. Data ownership

The synchronization plane stores domain events and snapshots, not raw provider credentials, Windows DPAPI-protected role memories, local tool output directories, or raw Pi session files. Large artifacts should be referenced by scoped object identifiers. Secrets and current Windows role memory stay with the Runtime Host/Windows owner unless a future normalized, encrypted cross-device contract is explicitly designed.

Windows local storage has two independent version and recovery domains. The implemented `roundtable.db` v2 owns normalized meeting events, receipts, checkpoints, and DPAPI-protected role-memory revisions; initialization validates its exact declared schema and v1→v2 migration is atomic. The reviewed but still planned v3 adds private memory candidates, recall audits, role-context snapshots, and retention jobs without changing `protocol/schema`. The separately planned `platform.db` owns module/catalog state, content-addressed artifact metadata, worker jobs, private diagnostics retention, backup metadata, and its own migration journal; none of those records may be mixed into meeting storage. The complete ownership, backup, and forward-migration contract is recorded in [ADR 0013](adr/0013-local-database-ownership-and-forward-migrations.md).

## 6. Agent execution model

Each active role owns an isolated runtime session supervised by the meeting Runtime Host. The meeting orchestrator decides who may speak, create a temporary role, invoke a capability, or retain a role; the model runtime does not become the authorization layer. Tools start disabled and are exposed through explicit role- and meeting-scoped capabilities. Commands carry stable IDs so retries do not duplicate model or tool work.

Normalized domain events are the authoritative meeting history. Provider transcripts, reasoning records, caches, tool arguments/results, and Pi private sessions are private runtime state. Windows durable checkpoints, crash-safe command receipts, human approval before granted MCP tools, MCP consent boundaries, and deterministic discussion/observer budgets are implemented. The relay's authenticated PostgreSQL storage boundary is implemented and locally verified, while Windows/Android authenticated recovery over that relay remains pending. OpenTelemetry GenAI spans and content-safe diagnostics export remain planned integration surfaces; their schemas must remain additive and must not weaken `runtimeGeneration` fencing.

## 7. Windows packaging boundary

The x64 alpha is published framework-self-contained and Windows App SDK-self-contained. The repository-root `VERSION` is the current build version consumed by CMake, MSBuild, WiX, packaging scripts, and CI; a crash-recoverable, idempotent set/check transaction keeps npm workspace/lock metadata and the Runtime Host identity synchronized and enforces the Windows Installer numeric range. The separately signed stable update manifest remains bound to the actually published asset and is intentionally not rewritten during a candidate version bump. The MSI bundles the generated WinUI XBF/PRI resources, the release C++ core, a Node 24 executable, the compiled Runtime Host, the protocol package, and production Pi/MCP dependencies. The staging step removes source maps, TypeScript declarations, and build metadata only from the copied runtime tree, then executes Node syntax and production-module import smoke checks before WiX harvesting. Packaged path resolution always prefers these adjacent assets and does not depend on a repository checkout, inherited development overrides, or machine-wide Node installation. The WiX 4 pipeline is implemented; its strict ICE03 warning allowlist, administrative extraction, and extracted-payload launch are verification gates. Suppressing MSI validation is permitted only after an equivalent release payload has passed those gates and is never itself a verification result. A separate updater validates a pinned ECDSA P-256 manifest signature, exact byte count, SHA-256, and optional Authenticode requirement before handing installation to a narrow helper. The client and helper share a dependency-free artifact-integrity library; it performs bounded copy, fixed-time digest checks, Windows no-follow reparse validation, parent path locking during verified open, and verified-handle lifetime without absorbing manifest trust, Authenticode policy, or installation authorization.

The same Windows-neutral distribution assembly now implements a version 1 signed-catalog contract and pure verifier for future updater, module-catalog, artifact-import, and offline-layout callers. Trust policy, time, key lifecycle, and the monotonic epoch/sequence floor are explicit inputs; strict JSON, ECDSA P-256, expiry, same-origin asset, safe-name, size, and SHA-256 checks produce immutable normalized values or closed credential-free diagnostics. The verifier performs no I/O and is not connected to catalog refresh or module installation; its boundary is recorded in [ADR 0011](adr/0011-signed-catalog-trust-boundary.md). The distribution assembly also implements a separate Windows-only, handle-owned staging transaction: it locks every destination directory component, creates no-follow leaves, retains one file object through copy, post-flush verification, Authenticode, and atomic promotion, serializes concurrent writers with a crash-released directory lease, and recovers strictly named orphan leaves. A failed replaceable state sidecar preserves the verified package for locked offline repair. Sustained fuzzing and forced process termination throughout the commit region remain pending; the staging boundary is recorded in [ADR 0012](adr/0012-handle-owned-windows-artifact-staging.md).

First-party executable artifacts are signed after publication and before the WiX file manifest is generated; the MSI is signed only after linking, and release hashes are calculated after signing. Production signing requires a repository-external code-signing identity, an RFC 3161 timestamp, and Windows trust verification. Pull-request CI only creates a non-exportable ephemeral certificate to prove the signing order and signature-presence checks; it is not a production identity. MSI lifecycle tests use a dedicated product name, UpgradeCode, install directory, registry path, and output tree so they cannot upgrade or remove the production product. The state machine covers install, responsive launch, file repair, major upgrade, downgrade blocking without mutation, second repair, uninstall, and residual cleanup. This isolated state-machine evidence is deliberately distinct from a clean-VM production stable-to-candidate upgrade. Release evidence is content-addressed: production build, clean-VM lifecycle, and real-DPI visual reports must agree on current `VERSION`, the immutable Git commit, and signed artifact SHA-256 values; command success is only `passed`, while `verified` is reserved for parsed evidence satisfying that identity contract. Heavy WiX staging uses a unique short ignored work path because legacy ICE subprocess plumbing fails on deeply nested harvested source paths; durable reports keep the full run identity and record that work path. CI uses bounded shortcuts after equivalent checks and therefore is not a Release Candidate gate. ARM64 packaging remains pending.
