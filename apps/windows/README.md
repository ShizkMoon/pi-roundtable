# Windows client

Native C#/WinUI 3 client for the first desktop Runtime Owner. The implemented local client starts the stdio Runtime Host, creates long-term and temporary roles, promotes or archives roles, streams normalized speech events, and supports cancellation and explicit interruption. It applies events to the C++ core before changing visible state. A DPAPI-protected SQLite event store persists normalized events and checkpoints so a paused or interrupted live meeting can replay accepted history and resume under the next `runtimeGeneration`.

The project targets .NET 10 LTS and Windows App SDK 2.3.1. The repository `global.json` pins the verified .NET 10 feature band while allowing servicing patches. The current workstation has the required .NET SDK; WinUI restore/build verification still depends on the installed Visual Studio workloads and package restore.

The implemented first installer target is an unsigned x64 MSI containing the .NET runtime, Windows App SDK, Node 24 runtime, Pi Runtime Host, and native meeting core. `scripts/build-windows-x64.ps1` builds and verifies the code, publishes the self-contained WinUI resources, stages production Node dependencies, and generates the MSI through WiX 4. Provider/model persistence, provider model-list discovery/import, and API-key storage in Windows Credential Manager are implemented. Git Skill/MCP imports use a bounded temporary checkout, a redacted LLM review snapshot, an isolated atomic catalog install, and an explicit disabled-until-approved lifecycle. Interactive MCP tool approval exposes only sanitized server/tool identity to the host; arguments and results remain private. Pi SubAgents are isolated, cannot recurse, expose bounded progress, and return their result only to the parent role. Signing, ARM64 native-core packaging, and a real install/uninstall plus upgrade/repair matrix remain pending.

For development, build TypeScript and C++ before building/running WinUI. The x64 project copies `out/build/dev/core/pi_roundtable_core.dll` beside the application when it exists. The client locates `packages/runtime-host/dist/host-main.js` by walking to the repository root; packaged-path overrides are available through `PI_ROUNDTABLE_RUNTIME_HOST_SCRIPT` and `PI_ROUNDTABLE_NODE_PATH`. A packaged build instead resolves `runtime/node.exe` and `runtime-host/host-main.js` beside the application, so end users do not need Node or the repository checkout.
