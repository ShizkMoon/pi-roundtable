# Windows client

Native C#/WinUI 3 client for the first desktop Runtime Owner. The implemented local client starts the stdio Runtime Host, creates long-term and temporary roles, promotes or archives roles, streams normalized speech events, and supports cancellation, explicit interruption, facilitated agenda/free-discussion/convergence modes, budgeted role floor requests/critical抢答, and automatic anti-loop convergence or pause. A compact adaptive strip exposes the current mode, agenda item, turn/round/interruption budget, queue, and direct host controls without a separate responder selector. The client applies events to the C++ core before changing visible state. A DPAPI-protected SQLite event store persists normalized events and checkpoints so a paused or interrupted live meeting can replay accepted history, reconstruct the scheduler snapshot, and resume under the next `runtimeGeneration`.

The current application-service extraction routes commands through `MeetingCommandGateway`, accepted events through `MeetingProjectionController`, recovery through `MeetingSessionController`, and session move/delete through `SessionLifecycleController`. Workspace, role-profile, and catalog use cases also sit behind controllers. Closed diagnostics cover stale-generation drops, duplicate/gapped sequences, persistence failures, and projection failures without retaining private payloads. Full runtime start/pause/close orchestration is still scaffolded in the presentation adapter; a decreasing `MainViewModel` line budget prevents that remaining work from silently growing.

`roundtable.db` v3 implements encrypted review candidates, append-only recall audits, context-snapshot and retention-job contracts, and the existing immutable memory revisions. The memory panel connects manual candidate submission, approve/reject, edit, history, supersede/restore, and provenance. Each role start freezes at most four active revisions within 6,000 characters and sends them only through the private Runtime Host initialize frame; edits affect the next role start. Meeting-close candidate generation, automated safety scanning, retention controls, backup/restore, and corruption quarantine remain pending.

The public composer connects attachment selection, bounded preflight, explicit confirmation, removal/cancellation, retry, and send-failure preservation. Confirmed inputs are re-hashed into a private SHA-256 CAS indexed by the minimal `platform.db` artifact schema, with a 256 MiB default quota, unbound-LRU cleanup, orphan reconciliation, and meeting reference tracking. PDF remains metadata-only and TeX remains inert source. Private-composer attachments, previews, general artifact workers, retention, and backup/restore remain pending. Session group moves persist immediately; deletion shows a data-impact summary, removes all meeting-owned event/memory-support/artifact state, preserves shared role profiles/memories/credentials, and uses staged restart recovery if cleanup is interrupted.

The project targets .NET 10 LTS and Windows App SDK 2.3.1. The repository `global.json` pins the verified .NET 10 feature band while allowing servicing patches. The current workstation has the required .NET SDK; WinUI restore/build verification still depends on the installed Visual Studio workloads and package restore.

The implemented first installer target is an x64 MSI containing the .NET runtime, Windows App SDK, Node 24 runtime, Pi Runtime Host, and native meeting core. `scripts/build-windows-x64.ps1` builds and verifies the code, publishes the self-contained WinUI resources, stages production Node dependencies from the reviewed `packaging/windows-runtime/package-lock.json` with `npm ci` and lifecycle scripts disabled, and generates the MSI through WiX 4. Its ICE03 allowlist is a strict gate; suppressing MSI validation is not a verified ReleaseCandidate path. The payload has optional Authenticode hooks, an isolated MSI install/repair/upgrade/downgrade-block/uninstall harness, and strict optional visual-report aggregation. The desktop updater uses `PiRoundtable.Distribution` for no-follow directory/leaf locks, cross-process staging serialization, crash-orphan cleanup, and same-handle atomic promotion. The updater and independent elevated helper share its bounded byte transfer, immutable size/SHA-256 expectations, fixed-time digest verification, and verified-handle lock; ECDSA manifest trust, redirect rules, optional Authenticode policy, process fencing, and install authorization remain in their owning components. The required personal-project ReleaseCandidate reruns the complete self-contained payload lifecycle on the current Windows workstation, including responsive launch and zero QA residue. A trusted signing certificate, disposable clean VM, real-provider scenario, and separate 100%/150%/200% DPI sessions remain available as optional diagnostics and do not block publication. Provider/model persistence, provider model-list discovery/import, and API-key storage in Windows Credential Manager are implemented. Git Skill/MCP imports use a bounded temporary checkout, a redacted LLM review snapshot, an isolated atomic catalog install, and an explicit disabled-until-approved lifecycle. Interactive MCP tool approval exposes only sanitized server/tool identity to the host; arguments and results remain private. The built-in `provider.web_search` capability is exposed only to granted tool-calling OpenAI routes allowed by workspace network policy; direct roles reuse interactive approval and isolated SubAgents require pre-approved execution. Pi SubAgents cannot recurse, expose bounded progress, and return their result only to the parent role. ARM64 native-core packaging and its architecture-matched updater helper remain pending.

For development, build TypeScript and C++ before building/running WinUI. The x64 project copies `out/build/dev/core/pi_roundtable_core.dll` beside the application when it exists. The client locates `packages/runtime-host/dist/host-main.js` by walking to the repository root; source checkout and test overrides are available through `PI_ROUNDTABLE_RUNTIME_HOST_SCRIPT` and `PI_ROUNDTABLE_NODE_PATH`. A packaged build always prefers `runtime/node.exe` and `runtime-host/host-main.js` beside the application and therefore ignores those inherited override variables, so end users do not need Node or the repository checkout.
